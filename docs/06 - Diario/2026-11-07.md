# Sesión — 2026-11-07

## Contexto

Fase 1.3: `TenantContext`, resolución de la mancomunidad activa y filtro base de aislamiento, todavía sin autenticación. El tenant se simula con una cabecera para poder probar el aislamiento antes de la Fase 2. Después se añade el frontend Angular, la home que comprueba el health y los pipelines de CI/CD.

### Fase 1.3 — TenantContext y aislamiento base

- Paquete `com.mancomunidad.tenant`:
  - `TenantContext`: contexto por hilo con la mancomunidad activa y limpieza obligatoria.
  - `TenantResolver` y `HeaderTenantResolver`: resolución provisional por `X-Mancomunidad-Id`, validando que la mancomunidad existe y está activa.
  - `TenantFilter`: rellena el contexto antes de la cadena y lo limpia siempre al terminar; solo actúa sobre `/api/`.
  - `MancomunidadActual`, `MancomunidadActualService` y `TenantController`: `GET /api/v1/tenant/actual`.
  - `TenantNoResueltoException` y `TenantExceptionHandler`: `404` con Problem Details y `code = TENANT_NO_RESUELTO`.
- `app.tenant.header-enabled` es `false` por defecto y `true` en `dev` y `test`. En producción el controlador y el resolutor no se registran.
- `V3__segunda_mancomunidad_demo.sql` en `db/dev`: `demo-b` (`DANZA`) con su curso `2026-2027` activo y sin usuarios, para probar el aislamiento.
- Tests: `TenantContextTests` y `TenantEndpointTests`, además del seed de la versión 3 en `MigracionesTests`. **13 tests en verde.**
- Verificado con `docker compose up -d` (esquema en la versión 3) y con el backend en marcha: la cabecera correcta devuelve `200` y su ausencia `404`.

### Fase 1.4 — Frontend Angular y home con health

- Proyecto `frontend/` con Angular CLI 22.2.6: standalone, routing, SCSS, builder `@angular/build` y Vitest.
- Estructura `core/salud` (`SaludService`, `EstadoSalud`) y `features/inicio` (home lazy con `loadComponent`).
- Home accesible con `OnPush` y signals: estado `cargando`/`Disponible`/`No disponible`, `aria-live="polite"`, última comprobación y botón de reintento.
- `proxy.conf.json` reenvía `/api` y `/actuator` a `localhost:8080` y está configurado en `angular.json`; `provideHttpClient()` en `app.config.ts`.
- Tests de servicio y home con `HttpTestingController`: **5 tests en verde**; `npm run build` correcto.
- Verificado con ambos servidores: la home se sirve en `localhost:4200`, el health responde a través del proxy y `GET /api/v1/tenant/actual` sigue devolviendo el tenant de la cabecera.
- README raíz con el arranque en tres comandos y README propio del frontend.

### Fase 1.5 — CI/CD, formato e imágenes Docker

- `.github/workflows/ci.yml` con cuatro jobs: backend (`./mvnw -B verify` con JDK 21 y Testcontainers), frontend (`npm ci`, lint, formato, Vitest y build con Node 26), Flyway (MySQL 8.4 efímero + `migrate` y `validate`) y Docker (buildx construye ambas imágenes).
- `.github/workflows/cd.yml` manual o por etiqueta `v*`: publica las imágenes en GHCR con tag de versión y SHA.
- Backend: Spotless 3.11 con Palantir Java Format, `removeUnusedImports`, limpieza de espacios y salto de línea final; se reformateó el código existente.
- Frontend: ESLint + Angular ESLint (`ng lint`), scripts de Prettier (`format` y `format:check`) y formato aplicado.
- `backend/Dockerfile` multi-stage (JDK 21 + JRE 21, usuario sin root, perfil `prod`) y `frontend/Dockerfile` (Node 26 + nginx 1.29) con `nginx.conf` que sirve la SPA y reenvía `/api` y `/actuator` a `backend:8080`.
- Verificación local: `./mvnw -B verify` (13 tests), lint, formato, tests de frontend (5) y build; `actionlint` sin errores; imágenes construidas y probadas juntas con nginx, health `UP` y API correcta.

## Decisiones

| Tema | Decisión |
| --- | --- |
| Mecanismo provisional | Cabecera `X-Mancomunidad-Id`, activa solo con `app.tenant.header-enabled=true` en `dev` y `test`; se elimina en la Fase 2 al leer el tenant del JWT. |
| Validación | La cabecera no se acepta a ciegas: se comprueba en base de datos que la mancomunidad existe y está activa. |
| Errores | Falta de tenant, tenant inexistente y cabecera inválida responden lo mismo (`404`), para no revelar información. |
| Contexto | `ThreadLocal` limpiado en `finally`; el `mancomunidadId` nunca llega desde el cuerpo de la petición. |
| Seeds | `demo-b` no tiene usuarios: existe solo para detectar cruces entre tenants en los tests. |
| Proxy | `/api` y `/actuator` se reenvían al backend en desarrollo; el health no vive bajo `/api`, pero la home lo necesita sin CORS. |
| Frontend | Angular standalone, `OnPush`, signals y rutas lazy; Material se añadirá cuando una pantalla lo necesite. |
| Tests frontend | Vitest con `HttpTestingController`; no se levanta un backend real para la home. |
| Formato | Spotless con Palantir Java Format en el backend y Prettier en el frontend; ambos se comprueban en CI. |
| Lint frontend | ESLint con las reglas recomendadas de TypeScript y Angular, incluida accesibilidad de plantillas. |
| Flyway en CI | Se aplica el esquema sobre MySQL efímero y después se ejecuta `validate` para detectar migraciones pendientes. |
| CD | En la Fase 1 solo publica imágenes en GHCR; el despliegue remoto espera a la infraestructura de la Fase 10. |
| Perfil de la imagen | El contenedor del backend fuerza `prod` para no cargar el seed de `dev`; `header-enabled` sigue desactivado por defecto. |
